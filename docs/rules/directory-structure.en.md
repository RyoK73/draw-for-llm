# Directory Structure Convention - Vertical Codebase -

## Rules for Placing Directories and Files

### What

- Split folders based on **"what it does" (domain/feature)**, not **technical kind (component/hooks/utils)**

### Why

- Prioritize meaningful cohesion (login, widgets, etc.) over technical concerns (component/hook/util/lib)

| structure  | features                                                             | Pros                                                                 | Cons                                     |
| ---------- | --------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------- |
| horizontal | Split by *technical kind*, e.g. `src/components,utils,hooks`          | Looks easy to understand at a glance                                  | References increase as code volume grows |
| vertical   | Split by *what it does*                                               | Changes stay localized to one place, lowering cognitive load          | Can be hard to judge the right categorization |

## `src/app/` is Routing Only

- Do not write logic or UI implementation directly in `page.tsx`/`layout.tsx`
- The implementation should just thinly import from the corresponding `src/{vertical name}/`
- Do not place files unrelated to routing under `app`/`login`/etc.
- Mixing in logic causes routing definitions and feature implementation to bloat together, reducing readability

### Example

```bash
src/
├── app/                    # Next.js App Router only. A thin entry point for routing
│   └── login/
│       └── page.tsx
├── login/                  # A feature-based vertical. Everything related to login
│   ├── login-form.tsx
│   ├── login-form.test.tsx
│   ├── use-login.ts
│   ├── login-action.ts
│   ├── login-schema.ts
│   └── index.ts            # Public interface
├── design-system/          # Generic UI parts that don't belong to any domain
│   ├── ui/                 # Raw primitives generated by shadcn/ui
│   │   ├── button.tsx
│   │   └── dialog.tsx
│   └── primary-button.tsx  # Our own component wrapping ui/
├── utils/                    # Generic functions that don't belong to any domain
└── widgets/                # Example of an independent vertical used across multiple pages/features
```

## Create a `src/{vertical name}/` per Feature and Gather All Related Code There

This applies regardless of kind — component / hook / util / type / schema / action, etc.
Decide placement based on **"would this change together when the vertical (feature) changes?"**

### Example

For a login feature, gather form UI, validation, API calls, and related types all together under `src/login/`.

```bash
src/
├── login/                  # A feature-based vertical. Everything related to login
│   ├── login-form.tsx
│   ├── login-form.test.tsx
│   ├── use-login.ts
│   ├── login-action.ts
│   ├── login-schema.ts
│   └── index.ts            # Public interface
~~~~~
```

## Put Generic UI Parts in `src/design-system/`

- This is for reusable UI parts (Button, Input, Dialog, etc.) that don't depend on a specific feature or domain
- When wrapping a raw shadcn part to apply your own styling, place it separately right under `design-system/`

> Ex
> `design-system/ui/button.tsx` ← raw part
> `design-system/primary-button.tsx` ← after wrapping

### Handling shadcn/ui

- Place components generated by shadcn/ui as-is under `src/design-system/ui/`
- Change the `aliases` in `components.json` so that subsequent `npx shadcn add` runs also generate to the correct location automatically

```json
// components.json
"aliases": {
  "components": "@/src/design-system",
  "ui": "@/src/design-system",
  "lib": "@/src/design-system/lib",
  "utils": "@/src/design-system/lib/utils",
  "hooks": "@/src/design-system/hooks"
}
```

## Code Used by Multiple Verticals (Features) Should Become an Independent Vertical Itself

- This applies to things that don't belong to a specific feature but also aren't generic UI parts (e.g. a composite UI like `PageFilters` used across multiple pages)
- Instead of taking the easy route into a "common" folder, split it out as `src/<new vertical name>/`

## Make Each Vertical's Public Scope Explicit via `index.ts`

- Files used only internally within a vertical (detailed implementation of hooks, actions, etc.) should not be deep-imported from outside
- Only export from `index.ts` what you want other verticals to use

```ts
// src/login/index.ts
export { LoginForm } from "./login-form";
// use-login.ts, login-action.ts are private (internal to the vertical only)
```

> Under consideration: mechanically forbidding deep imports that bypass `index.ts`,
> e.g. via an ESLint rule (such as `eslint-plugin-boundaries`)

## Decision Flowchart (When Unsure Where to Place a Component)

1. **Is it a generic UI part with no logic, purely presentational?**
   → Put it in `design-system/`
2. **Is it specific to one feature (vertical) and not used elsewhere?**
   → Place it inside that feature's `src/<vertical name>/` (do not export it from index.ts)
3. **Is it a purpose-specific component used by multiple features?**
   → Make it independent as a new vertical itself (`src/<new vertical name>/`)

## Notes

- Determining the *correct vertical name/classification* is not easy. Discuss with the team as needed
- Dependencies need to be made explicit by operating this together with `index.ts`
